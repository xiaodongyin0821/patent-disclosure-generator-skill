# 专利技术交底书生成器

本技能用于把“零散技术材料”整理成“可交给专利代理人继续处理的中文发明专利技术交底材料”。

它不是一个独立商业产品，而是一个让智能助手稳定执行专利交底工作流的专业技能包：把通用对话变成可复用、可检查、可迭代的交底书生成流程。

本技能同时覆盖两条常见路径：

- **基于想法起草**：用户先有发明构思、技术路线或零散说明，再逐步补全成技术交底书。
- **基于既有算法反推专利主线**：用户已经完成算法、系统或 Agent 项目开发，后来才发现其中的原理、流程耦合、场景兼容性或鲁棒机制具有专利价值，需要从复杂实现中反向抽取真正值得保护的发明主线。

## 核心价值

直接让通用模型写交底书，常见问题是：用户不会问、模型容易直接成文、缺失事实被润色掩盖、图号术语前后不一致、工程补丁和核心发明点混在一起。对于已经完成的复杂算法或 Agent 项目，额外问题是：实现链路长、模块耦合强、兼容场景多，用户自己也很难判断哪些机制才是真正有专利价值的主线。

本技能的价值是把这些隐性风险显式化：

- **引导补全**：先识别缺失信息，再按最小必要原则追问。
- **主线提炼**：把代码、算法或碎片说明收敛成“技术问题-技术方案-技术效果”闭环。
- **逆向抽取**：从已完成算法、复杂工程流程或 Agent 创新链路中，反向提炼真正值得保护的技术原理，而不是简单复述实现细节。
- **专利性收束**：区分核心发明层、优选实施层和工程实现层，避免写成代码说明书。
- **图文一致**：统一正文图号、附图说明、图题、阶段流程和术语。
- **迭代审校**：支持基于旧版交底书继续优化，而不是每轮重写。
- **边界清晰**：只做技术交底辅助，不替代专利代理人的法律判断、权利要求布局和授权评估。

一句话：本技能不承诺“自动写出可授权专利”，而是帮助用户更快形成一份逻辑清楚、材料完整、便于代理人接手的技术交底稿。

## 何时使用

在用户提出以下需求时使用：

- “根据这段算法/代码写一份发明专利技术交底书”
- “这个项目/Agent 已经做完了，请从现有算法中抽取有专利价值的技术主线”
- “基于旧版交底书继续优化”
- “补全公式、参数说明、变量定义”
- “检查正文与附图是否一致”
- “区分哪些是核心发明点，哪些只是工程补丁”
- “把零散研发材料整理成可交给代理人的交底书”

不用于：

- 正式法律授权结论
- 独立权利要求和从属权利要求的最终法律撰写
- 侵权判断或 FTO 分析
- 与技术交底无关的普通文案整理

## 使用模式

根据用户输入状态选择一种模式，不要机械套模板。

### 1. 材料梳理模式

适用于用户只有零散想法、代码片段、实验记录或口头描述。

先输出：

1. 已知技术事实
2. 可能的发明主线
3. 关键缺口
4. 最小必要追问

不要一上来写完整交底书。信息不足时，先追问会影响主线判断的问题。

### 2. 想法起草模式

适用于用户已经提供较完整材料，或明确要求直接起草。

先提炼发明主线，再按交底书结构输出。稳定章节骨架见 [references/输出模板.md](references/输出模板.md)。

### 3. 算法反推模式

适用于用户已经完成算法、系统或 Agent 项目开发，希望从现有实现中反推出专利价值。

重点任务：

- 从复杂实现中识别真正产生效果的关键技术关系
- 区分“可保护的原理链”与“普通工程实现”
- 从多模块耦合、场景兼容、鲁棒处理、反馈闭环中提炼发明点
- 避免把现成代码逐行翻译成交底书

这一模式下，优先追问：

- 哪些效果是显著优于常规方案的
- 哪些机制是为了解决特定复杂场景而设计的
- 哪些模块之间存在关键依赖、反馈、约束或恢复关系
- 哪些部分只是为了工程落地、兼容或加速

### 4. 旧版迭代模式

适用于用户提供旧版交底书并要求优化。

重点检查：

- 旧版主线是否偏离真正发明点
- 是否残留旧术语、旧图号、旧逻辑
- 公式和变量是否完整
- 附图说明与正文是否同步
- 用户新增偏好是否已经贯彻

如需多轮反馈沉淀规则，读取 [references/迭代示例模式.md](references/迭代示例模式.md)。

### 5. 公式与参数审校模式

适用于用户要求补公式、统一符号、解释参数。

要求：

- 每个公式说明变量含义、输入、输出、适用条件
- 解释本阶段结果如何进入下一阶段
- 避免堆砌数学符号而不说明技术作用

细则见 [references/公式审校.md](references/公式审校.md)。

### 6. 附图一致性模式

适用于用户提供附图、流程图、图号或要求统一图文。

检查：

- 正文首次出现图号顺序是否正确
- 图题、图位、附图说明是否一致
- 图中阶段是否与正文步骤对应
- 图仅为示意时是否说明“仅示部分”

细则见 [references/附图规则.md](references/附图规则.md)。

### 7. 最终审校模式

适用于交付前检查。

按四条闭环复核：

1. 技术问题闭环：背景缺陷、发明目的、技术方案、技术效果是否互相回应。
2. 区别特征闭环：真正区别于现有技术的结构、流程或参数关系是否突出。
3. 公式变量闭环：每个公式是否有完整变量定义、输入输出和适用条件。
4. 图文一致闭环：正文图号、附图说明、图题和阶段流程是否一致。

最终审校细则见 [references/最终审校.md](references/最终审校.md)。

## 标准工作流

### 第一步：判断输入成熟度

将材料分为三类：

- **A 类：可直接起草**：有技术问题、核心步骤、实施例和效果描述。
- **B 类：需补充后起草**：有方向但缺核心参数、实验效果或步骤关系。
- **C 类：仅能梳理问题**：只有想法、代码片段或模糊目标。

A 类可以起草；B 类先追问关键缺口；C 类先做材料梳理，不硬写最终版。

### 第二步：提炼发明主线

优先回答：

- 现有方法解决不了什么
- 本发明到底解决什么
- 核心区别特征是什么
- 哪些内容只是工程实现，不应进入主线

更集中判断专利性时读取 [references/专利性主线提炼.md](references/专利性主线提炼.md)。

对于“算法反推模式”，尤其要判断：

- 哪些效果来自真正的新技术关系，而不是调参结果
- 哪些复杂流程是为了处理特殊场景兼容性、鲁棒性或闭环恢复
- 哪些模块间的前后依赖，才是值得保护的创新主线

### 第三步：分层表达

默认分三层：

1. **核心发明层**：真正支撑专利性的技术主链。
2. **优选实施层**：参数、增强机制、补充处理、替代实现。
3. **工程实现层**：平台兼容、批处理、路径处理、可视化工具、环境修补。

交底书主线优先写第一层，第二层作为实施例，第三层谨慎写入。

### 第四步：生成或迭代正文

正文应使用正式中文专利交底语气，章节承接自然，术语稳定，以结构化技术表达为主。

避免：

- 论文式空泛综述
- 代码注释式流水账
- 法律权利要求腔过重
- 营销式夸张表达
- 把未提供的数据写成确定结论

### 第五步：交付前复核

如果任一闭环不成立，先列“待补材料 / 待确认问题”，不要硬写成最终版。

## 用户输入引导

如果用户材料不完整，按最小必要原则提问。优先问会影响发明主线的问题，不要一次性抛出长问卷。

可追问：

1. 这是新起草还是旧版优化？
2. 技术对象是什么：算法、检测方法、控制方法、系统方案，还是硬件结构？
3. 现有方案的主要缺陷是什么？
4. 本方案最关键的区别步骤/模块是什么？
5. 每个关键步骤的输入、处理、输出是什么？
6. 技术效果有什么实验或工程现象支撑？
7. 是否有附图、流程图、检测图或示意图？
8. 哪些内容只是工程兼容或实现细节，不希望写成主发明点？
9. 如果方案已经开发完成，哪些模块耦合、恢复机制、场景兼容或反馈闭环是效果显著提升的关键来源？
